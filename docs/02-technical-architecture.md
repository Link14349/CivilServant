# 技术架构设计

## 1. 架构目标

系统必须同时满足：

- 支持预设选项和玩家自由文本；
- NPC 有局部知识、持续关系和跨回合记忆；
- LLM 输出失败或波动时，世界状态仍然一致；
- 相同初始状态、相同玩家结构化行动和相同随机种子可以复现结算；
- 网页端能够流式展示材料、对话和回合结算；
- 第一版足够简单，可在本地单机运行；
- 后续能够替换模型供应商、数据库和部署方式。

## 2. 核心技术决策

### 2.1 选定技术栈

| 层 | MVP 方案 | 后续扩展 |
|---|---|---|
| 后端 | Python + FastAPI | 保持 Python，按需拆分后台任务进程 |
| 数据校验 | Pydantic | 保持结构化契约 |
| ORM/迁移 | SQLAlchemy + Alembic | SQLite 迁移到 PostgreSQL |
| 数据库 | SQLite | PostgreSQL |
| 前端 | React + TypeScript + Vite | 保持 SPA，按需要增加状态管理 |
| 回合流式输出 | Server-Sent Events（SSE） | 只有双向实时需求出现时才使用 WebSocket |
| LLM | 自定义 Provider Adapter | 可接不同 Responses/Chat API 或本地模型 |
| 测试 | pytest + 前端组件/端到端测试 | 增加回放、负载和模型评测 |

实现时使用当时受支持的稳定版本并锁定依赖，不在设计文档中绑定尚未验证的具体版本号。

### 2.2 为什么不是“全 Agent 自由运行”

所有常驻 Agent 自主循环会带来成本高、不可复现、相互矛盾和无关内容过多的问题。MVP 使用**事件驱动激活**：

- 只有与当前议题相关的人物进入本回合推理；
- Agent 只能提出立场、计划、材料和表达；
- Agent 不能直接修改数据库；
- 所有状态变化必须通过结构化命令交给模拟内核；
- 模拟内核验证权限、资源、程序和因果后再提交。

## 3. 系统边界

```text
┌────────────────── Web Browser ──────────────────┐
│ React UI：材料、人物、会谈、指令、方案、结算   │
└──────────────────────┬──────────────────────────┘
                       │ HTTP + SSE
┌──────────────────────▼──────────────────────────┐
│ FastAPI API / Application Service               │
│ 会话、鉴权边界、命令幂等、回合编排、流式事件    │
├──────────────┬───────────────┬──────────────────┤
│ Simulation   │ Agent Runtime │ Content Runtime  │
│ 权限/资源/   │ 相关NPC、     │ 场景、规则、     │
│ 规则/结算    │ 文书、叙事    │ 事件模板         │
├──────────────┴───────────────┴──────────────────┤
│ Repositories / Event Log / Snapshot Store       │
└──────────────────────┬──────────────────────────┘
                       │
                 SQLite / PostgreSQL
```

### 3.1 前端职责

- 展示已公开给玩家的信息；
- 收集选项、自由文本、追问和授权决定；
- 展示流式生成进度，但不自行计算世界结果；
- 保存草稿和界面状态；
- 对失败回合提供安全重试，不重复提交命令；
- 明确区分“已知事实”“人物观点”“系统提示”。

### 3.2 API/Application Service 职责

- 创建和载入游戏会话；
- 验证玩家当前是否允许执行该动作；
- 为每次命令分配幂等键；
- 调用回合编排器并发送进度事件；
- 在一个事务中提交事件日志和新快照；
- 隐藏玩家尚未获得的世界事实。

### 3.3 模拟内核职责

- 权限和程序校验；
- 资源预算和时间推进；
- 注意力消耗；
- 方案可行性计算；
- NPC 非语言层面的立场和行动约束；
- 指标、关系、承诺、证据和风险更新；
- 使用带种子的伪随机数处理不确定事件；
- 生成结构化结果，不负责文学表达。

### 3.4 Agent Runtime 职责

- 将自由文本解析为受约束的领导指令；
- 按角色认知生成材料、方案、对话和解释；
- 为相关 NPC 提议行动；
- 将结构化结果转写为可读叙事；
- 压缩长期记忆，但不得删除仍有效的承诺、证据和任务。

### 3.5 Content Runtime 职责

- 载入虚构场景包；
- 管理事件模板、人物模板和规则引用；
- 触发满足条件的事件链节点；
- 验证内容引用的实体和指标是否存在；
- 支持后续通过数据文件增加场景，而不修改模拟代码。

## 4. 领域模型

### 4.1 聚合根

`GameSession` 是单局游戏的聚合根，包含：

- 场景包版本；
- 当前游戏时间和回合阶段；
- 随机种子及随机流位置；
- 当前世界快照版本；
- 玩家所任职位；
- 尚未完成的议题和允许动作；
- 最新已提交事件序号。

### 4.2 核心实体

| 实体 | 作用 |
|---|---|
| `Jurisdiction` | 城市、区县和机构层级 |
| `Actor` | 官员、企业负责人、社会代表等人物 |
| `Office` | 市委、市政府、部门、区县、企业等组织 |
| `RoleAssignment` | 人物在某时段担任的职务和权限 |
| `Authority` | 召集、建议、批准、执行、否决、监督等权限 |
| `RelationshipEdge` | 两名人物之间按议题区分的信任、依赖和竞争 |
| `Belief` | 某人物对一个事实的认知、置信度和来源 |
| `Report` | 呈给玩家或其他人物的材料版本 |
| `Issue` | 可持续多个回合的政策问题或危机 |
| `Directive` | 玩家或上级提出的目标、红线和授权 |
| `Proposal` | NPC 根据指令形成的实施方案 |
| `Decision` | 经审议后获得正式效力的选择 |
| `Commitment` | 对人物或机构作出的未来承诺 |
| `ResponsibilityRecord` | 会议、签字、公开讲话形成的责任痕迹 |
| `Evidence` | 审计、举报、纪要、数据差异等可被发现的痕迹 |
| `Project` | 有预算、期限、进度和责任单位的实施对象 |
| `Metric` | 财政、就业、环境、信任、行政能力等状态 |
| `DomainEvent` | 已发生且不可修改的事实记录 |
| `Memory` | 人物可用于语言推理的摘要，不代替正式状态 |

### 4.3 事实、认知和报告

系统禁止把世界事实直接复制给所有 Agent。

```text
WorldFact
  ├── Actor A Belief：知道但低估严重性
  ├── Actor B Belief：准确知道但选择隐瞒
  └── Player Report：经过部门汇总后的第三个版本
```

`Belief` 必须包含来源、获得时间和置信度。材料生成 Agent 只能读取该角色有权知道的事实与认知。

## 5. 结构化契约

### 5.1 领导指令

玩家自由输入不会直接成为世界命令。解析器首先生成候选 `Directive`：

```json
{
  "objective": "按期完成第一阶段整改，同时避免集中失业",
  "priorities": ["合规", "就业稳定"],
  "red_lines": ["不得新增隐性债务", "不得伪造排放数据"],
  "delegate_to": "mayor",
  "requested_options": 3,
  "report_deadline_days": 14,
  "required_risk_sections": ["财政", "就业", "信访"],
  "ambiguities": []
}
```

如果自由文本缺少不影响方向的细节，由下属补充；如果缺少会彻底改变意图的关键选择，界面只追问一个必要问题。

### 5.2 实施方案

`Proposal` 由被授权的 NPC/机构提出，而不是由自由文本解析器代替玩家暗中补完：

```json
{
  "sponsor": "mayor",
  "owners": ["executive_vice_mayor", "industry_bureau"],
  "steps": [],
  "funding": [],
  "timeline": [],
  "stakeholder_impacts": [],
  "legal_or_policy_risks": [],
  "assumptions": [],
  "disagreements_requiring_player": []
}
```

### 5.3 NPC 行动提议

LLM 只能从允许的动作类型中提议，例如：支持、附条件支持、请求修改、拖延、独立核查、选择性汇报、向他人游说、申请上报。模拟内核验证该人物是否有能力、信息和动机执行。

### 5.4 回合结算

结算结果区分：

- 已确定的结构化状态变化；
- 玩家立即能够知道的信息；
- 暂时隐藏的变化；
- 新形成的承诺和证据；
- 已安排的延迟事件；
- 供叙事器使用但不能改写的事实清单。

所有 LLM 输出均通过 Pydantic 模型校验。校验失败时先进行有限次数的结构修复；仍失败则使用模板化降级结果，不提交半完成状态。

## 6. 回合编排

### 6.1 提交玩家动作

1. API 接收玩家动作和客户端幂等键。
2. 检查会话版本，防止对过期页面重复决策。
3. 自由文本经过指令解析；预设选项直接映射为同一结构。
4. 向玩家展示解析摘要；MVP 默认仅在存在关键歧义时要求确认。

### 6.2 形成方案和反应

1. 从当前议题计算相关人物集合。
2. 读取每人的有限视图，而非完整世界状态。
3. 被授权者起草实施方案。
4. 其他关键人物分别给出立场和条件。
5. 规则层检查权限、资源、时间和程序。
6. 对明显不可行部分返回给方案起草者修订一次；不允许无限 Agent 对话。

### 6.3 结算与提交

1. 模拟内核计算基础结果。
2. 通过种子随机流处理不确定性。
3. 生成 `DomainEvent` 列表和新快照。
4. 叙事器只基于已确定事件生成文字。
5. 在单个事务中写入事件日志、快照和玩家可见消息。
6. SSE 推送完成事件，前端刷新视图。

### 6.4 中断和失败

- LLM 超时不推进游戏时间；
- 相同幂等键重试不会再次扣除注意力；
- 只有结构化结算成功后才提交新快照；
- 叙事失败可在不重新结算的情况下单独重试；
- 每次回合保留模型调用元数据和 Prompt 版本，但日志不记录密钥。

## 7. Agent 类型

### 7.1 指令解析器

将玩家自由文本转换为领导层意图，不自行设计完整政策。它必须标注：明确内容、合理默认、关键歧义和越权/不可行诉求。

### 7.2 办公厅/秘书 Agent

负责整理议程、提炼材料矛盾、形成待拍板事项。它不掌握世界真相，只能使用其渠道获得的信息。

### 7.3 方案起草 Agent

代表被授权的市长、分管领导或部门形成实施方案。起草结果同时受到角色能力、利益和认知限制。

### 7.4 NPC 决策 Agent

为关键人物生成立场、条件、对话和可选行动。稳定人格来自结构化配置，LLM 不得每回合重写其核心价值。

### 7.5 事件导演

从已满足的内容触发条件中选择适合当前节奏的事件节点。它可以排序，不能凭空创造未在内容规则中允许的重大资源或制度变化。

### 7.6 叙事器

生成批示、汇报摘要、会议片段、私人谈话和回合总结。叙事器接收不可修改的结算事实，并必须区分事实、传闻和人物观点。

### 7.7 记忆压缩器

将冗长对话压缩成角色记忆。正式承诺、责任记录、证据、任务和指标永远保存在结构化状态中，不能只依赖摘要。

## 8. 确定性与随机性

- 每局在创建时生成一个主随机种子；
- 不同子系统使用独立派生随机流，例如执行、事故、信息泄露；
- 随机抽样发生在模拟内核，不由 LLM 用语言决定；
- 事件日志保存抽样标签和结果，方便回放；
- LLM 文字不要求逐字可复现，但其结构化输入、结算和状态变化必须可复现。

不得以一个简单成功率替代全部机制。执行结果应先由资源、能力、支持和阻力计算基线，再在有限范围内加入随机冲击。

## 9. 持久化策略

MVP 使用事件日志加周期快照：

- `DomainEvent` 只追加，不修改；
- 每个完成回合产生一个完整世界快照；
- 读取时优先载入最新快照，并按需要追加事件；
- 存档导出包含场景版本、随机种子、事件日志和快照；
- 内容包升级不能静默改变旧存档的规则版本。

这样可以支持回放、问题诊断、平衡分析和未来的“从某一决策点重新开始”。

## 10. API 草案

MVP 只需要少量资源式接口：

- `POST /api/games`：创建游戏；
- `GET /api/games/{id}`：获取玩家可见快照；
- `GET /api/games/{id}/briefing`：获取当前回合材料；
- `POST /api/games/{id}/actions`：提交选项、自由文本或互动动作；
- `GET /api/games/{id}/stream`：SSE 进度和结果；
- `GET /api/games/{id}/actors/{actor_id}`：获取玩家已知的人物档案；
- `GET /api/games/{id}/issues/{issue_id}`：获取议题时间线；
- `POST /api/games/{id}/save-export`：导出存档。

接口返回玩家视图 DTO，不直接序列化内部领域实体，防止泄漏隐藏事实。

## 11. 网页端信息架构

### 11.1 主界面

- 顶部：时间、职位、当前阶段、剩余注意力；
- 左侧：本回合议程和待办事项；
- 中间：当前材料、对话、会议或方案；
- 右侧：相关人物、公开指标、承诺提醒；
- 底部：预设选项、“其他”输入和必要的目标/授权控件。

### 11.2 核心页面

- 开始新游戏；
- 晨报/议程；
- 材料阅读；
- 人物约谈；
- 领导指令；
- 方案比较；
- 会议决策；
- 回合结算；
- 人物关系与已知信息；
- 议题时间线；
- 存档管理。

### 11.3 交互原则

- 默认先给摘要，允许展开原始材料，避免大段文字淹没玩家；
- 自由输入与预设选项最终进入同一规则系统；
- 在提交前显示系统理解的目标和授权对象；
- 不显示隐藏好感度和精确成功率；
- 重要状态变化说明来源，例如“财政局测算”“秘书长私下提醒”；
- 对不能由当前职位直接决定的事项，界面引导玩家授权或协调，而不是简单报错。

## 12. 场景包

场景内容应以数据文件和版本化文本资源存放，预计包括：

- `scenario.yaml`：地区、时间、初始规则和指标；
- `actors/*.yaml`：人物稳定配置和初始认知；
- `issues/*.yaml`：事件链、触发条件和结果表；
- `reports/*.md`：可复用材料模板；
- `prompts/*.md`：版本化 Agent 指令；
- `schemas/`：内容校验模式。

具体格式在实现前以最小场景反推，不提前制作通用 DSL。

## 13. 安全与内容完整性

- 模型密钥仅从环境变量读取；
- 玩家文本、场景文本和模型输出均视为不可信输入；
- Agent 在 MVP 中没有文件系统、Shell、网络和数据库写权限；
- 所有数据库修改只能由应用服务调用领域命令完成；
- 日志脱敏，不记录模型密钥和不必要的玩家原文；
- 场景包不能通过文本指令覆盖系统权限；
- 真实人物信息不得混入虚构人物模板；
- 对违法内容保持描述性和后果导向，不生成规避审计、调查或执法的现实操作教程。

## 14. 测试策略

### 14.1 无 LLM 单元测试

- 权限判断；
- 注意力消耗；
- 资源和时间推进；
- 承诺履约与违约；
- 关系按议题变化；
- 事件触发条件；
- 同一随机种子的可复现性；
- 隐藏事实不会进入玩家 DTO。

### 14.2 LLM 契约测试

- 自由文本能否稳定解析为 `Directive`；
- 不会擅自补充关键政治选择；
- NPC 只能使用其已知信息；
- 叙事不改变结算事实；
- 结构校验失败能够降级；
- Prompt 版本更新使用固定样例进行回归评测。

### 14.3 集成测试

- 创建游戏到完成一个回合；
- 重复幂等请求不会重复结算；
- LLM 超时后安全重试；
- 存档导出和重新载入；
- SSE 中断后重新连接；
- 同一事件使用预设选项和等价自由文本得到相同的结构化意图。

### 14.4 游戏性测试

- 至少存在两种各有代价的合理策略；
- 玩家能够理解自己为何无法直接下达某项行政细节；
- 授权对象不同会实质改变方案；
- 一项承诺会在后续回合被人物记起；
- 坏结果能够追溯到信息、资源、关系或随机冲击，而非“LLM 说失败”。

## 15. 性能与成本

MVP 每个关键动作目标调用：

- 一次自由文本解析（仅自由输入时）；
- 一次方案起草；
- 一次批量或少量关键 NPC 反应；
- 一次叙事生成。

普通读材料、查看人物和选择已结构化选项不调用 LLM。生成中的中间文本可以流式展示，但只有最终校验通过的结构化输出能够进入状态。

## 17. 尚待验证的决策

- 自由文本解析摘要是否每次都需要玩家确认，还是仅关键歧义时确认；
- 约谈采用一次完整对话还是限制为若干轮问题；
- 关系状态应显示到什么程度；
- MVP 是否需要账户系统，默认倾向本地匿名存档；
- LLM 供应商和离线降级模型；
- 前端样式系统，在做出真实界面原型前不提前选定。
