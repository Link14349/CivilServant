# 技术架构设计

> 本文描述逐日开放模拟的架构边界。仓库已经实现首个按日 MVP；其中部分目标实体仍以 SQLite JSON 快照承载，将在首次需要独立表结构演进时引入 Alembic。

## 1. 架构目标

系统必须同时满足：

- 游戏按自然日长期推进，不依赖固定十二周事件脚本；
- 每天生成来源明确的晨报、文件、日程和待处理事项；
- 会议、面谈、调研、向上汇报和文件批阅都进入同一时间与权限系统；
- 每名 NPC 有独立身份、认知、记忆、文件权限、任务与行动能力；
- 多人会议支持并行判断发言意愿、流式发言和玩家中断；
- Agent 可以读写游戏内文件、与他人通气并提议行动，但不能直接改写世界；
- LLM 失败、超时、取消或输出波动时，世界状态保持一致；
- 相同初始状态、结构化行动和随机种子能够复现规则结算；
- 本地单机可运行，后续可替换模型、数据库和后台任务实现。

## 2. 核心技术决策

| 层 | 目标方案 | 说明 |
|---|---|---|
| 后端 | Python + FastAPI | API、应用编排与本地服务 |
| 数据契约 | Pydantic | API、Agent 输出和工具参数边界 |
| 领域模型 | 普通 Python | 不依赖 FastAPI、ORM 或具体模型 SDK |
| 数据库 | SQLite + SQLAlchemy + Alembic | 现有数据结构演进前先建立迁移 |
| 前端 | React + TypeScript + Vite | 严格模式，展示玩家视图 DTO |
| 实时交互 | HTTP 命令 + SSE 事件流 | 足以支持流式发言和独立的中断命令 |
| 后台任务 | MVP 使用进程内异步队列 | 后续可替换为持久任务队列 |
| LLM | Provider Adapter | 默认 DeepSeek V4 Flash |
| 测试 | pytest + 前端测试 + 回放测试 | 默认不访问真实模型或网络 |

默认模型：

- Base URL：`https://api.deepseek.com`；
- 模型：`deepseek-v4-flash`；
- 工具型 Agent 使用供应商原生 Tool Calls；没有工具的纯分类任务才请求结构化 JSON；
- 模型不可用时明确报错，不静默切换供应商；
- 模板模式在没有 Key 和网络时仍可运行逐日模拟。

## 3. 总体边界

```text
┌──────────────────────── Web Browser ────────────────────────┐
│ 日程 / 晨报 / 收件箱 / 会议室 / 会谈 / 调研 / 向上汇报   │
└───────────────────────────┬─────────────────────────────────┘
                            │ HTTP commands + SSE
┌───────────────────────────▼─────────────────────────────────┐
│ FastAPI API                                                     │
│ 会话版本、权限入口、命令幂等、流式任务控制、玩家视图          │
├───────────────┬────────────────┬────────────────────────────┤
│ Application   │ Agent Runtime  │ Content Runtime            │
│ 每日/场景编排 │ Context/Harness│ 场景、人物、事件候选与规则 │
├───────────────┴────────────────┴────────────────────────────┤
│ Domain Simulation                                             │
│ 时间、行动点、日程、会议权限、行动验证、结算、随机流          │
├──────────────────────────────────────────────────────────────┤
│ Repositories / Event Log / Snapshots / Virtual Document Store│
└───────────────────────────┬─────────────────────────────────┘
                            │
                   SQLite → PostgreSQL
```

### 3.1 不可跨越的边界

- API 只返回玩家有权看到的 DTO；
- Agent 不接收完整 `GameSession`，只接收经过投影的角色上下文；
- Agent 工具不直接写领域表，而是生成待验证的命令；
- 文件工具操作的是游戏内文档库，不是主机文件系统；
- 叙事只能描述已经结算的事实；
- 任何取消、超时或校验失败的生成都不能产生部分状态。

## 4. 应用服务划分

### 4.1 `DayOrchestrator`

- 创建当天行动点与状态；
- 执行预定日程；
- 接受玩家结束一天；
- 编排日终结算和次日晨报；
- 保证每天最多完成一次最终结算。

### 4.2 `SceneOrchestrator`

统一编排会议、个别会谈、上级面谈和调研中的互动生命周期：

- 建立场景参与者与可见范围；
- 管理发言顺序、流式任务和玩家中断；
- 冻结正式记录；
- 触发场景后结算；
- 将结构化结果一次性提交。

### 4.3 `ScheduleService`

- 建立、接受、改期、取消和触发日程；
- 预留未来行动点；
- 检查参与者可用性、地点和准备任务；
- 解决强制日程、上级召见和突发事件造成的冲突。

### 4.4 `BriefingAssembler`

只从玩家可见的新闻、文件、报告、日程、到期任务和传闻组装晨报。排序可以体现秘书系统偏好，但不得泄漏世界事实。

### 4.5 `DocumentWorkflowService`

管理文件版本、权限、送审、退回、签发、提交、转交和归档。它不负责决定文件内容是否真的产生政策效力；效力由领域权限和程序判断。

### 4.6 `AgentRuntime`

构建角色上下文、调用模型、暴露受限工具、校验输出、管理记忆检索和生成任务取消。

### 4.7 `SimulationKernel`

是唯一能够提交世界变化的组件：

- 权限与程序校验；
- 时间、行动点、工作量和资源消耗；
- 文件与决定的正式效力；
- NPC 行动意图的可执行性；
- 执行、信息传播和随机冲击；
- 任务、承诺、责任、证据、关系和指标更新。

## 5. 领域模型

### 5.1 聚合与主要实体

| 实体 | 作用 |
|---|---|
| `GameSession` | 场景版本、当前日期、随机流、玩家职位和最新事件序号 |
| `Day` | 当日阶段、行动点、晨报和已执行行动 |
| `CalendarEntry` | 日期、时段、行动、参与者、成本、强制性和冲突状态 |
| `BriefingEdition` | 某日晨报及其每条信息的来源 |
| `Actor` | 人物稳定身份和动态状态 |
| `RoleAssignment` | 职务、时段、组织和权限 |
| `ReferenceMaterial` | 玩家与所有角色共享的稳定公开背景资料 |
| `WorldFact` | 世界实际状态 |
| `Belief` | 某角色对事实的认知、置信度、来源和时间 |
| `Issue` | 可持续演化的问题、期限和关联主体 |
| `Task` | 起草、调查、协调、执行或报告任务 |
| `Meeting` | 制度类型、讨论方式、议题、人员、权限和记录 |
| `MeetingMaterial` | 发给一次会议的不可变文件版本快照、发送阶段和与会者知情范围 |
| `MeetingRound` | 发言意愿快照、随机抽样与最终发言 |
| `Conversation` | 面谈、通气或现场问答记录 |
| `FieldVisit` | 地点、通知方式、观察条件和结果 |
| `Document` | 文件逻辑身份 |
| `DocumentVersion` | 不可变内容、来源、权限和工作流状态 |
| `Submission` | 某个文件版本向特定对象的报送 |
| `Directive` | 目标、红线、授权和报告要求 |
| `Decision` | 经有权限程序形成的正式决定 |
| `Commitment` | 有条件或无条件的未来义务 |
| `ResponsibilityRecord` | 发言、表决、签发和公开承诺的责任痕迹 |
| `ActionIntent` | Agent 想采取但尚未生效的行动 |
| `DelayedTrigger` | 有条件、时间窗口、过期和取消规则的未来触发器 |
| `MemoryItem` | 角色的语义或情节记忆，不代替正式状态 |
| `PlayerNotebookNote` | 仅玩家可见的自由笔记，不进入 Agent 上下文或正式效力判断 |
| `DomainEvent` | 已经提交、不可修改的事实记录 |

### 5.2 日状态机

```text
MORNING_READY
  → REVIEWING
  → ACTION_PHASE
  ↔ SCENE_ACTIVE
  → END_DAY_REQUESTED
  → SETTLING
  → CLOSED
```

- `MORNING_READY`：晨报已经形成但尚未确认；
- `REVIEWING`：可处理文件和查看日程；
- `ACTION_PHASE`：可开始消耗行动点的活动；
- `SCENE_ACTIVE`：只有当前场景可以接收发言或结束命令；
- `SETTLING`：所有玩家写操作锁定；
- `CLOSED`：生成下一日后不再修改本日。

### 5.3 场景状态机

```text
DRAFT → SCHEDULED → ASSEMBLING → ACTIVE
                                  ↓
                           RECORD_FROZEN
                                  ↓
                         POST_SCENE_SETTLING
                                  ↓
                    COMPLETED / FAILED_WITHOUT_COMMIT
```

一个场景只能有一个有效的记录版本。失败发生在提交前则不扣行动点；开始后因玩家主动取消产生何种成本，由行动类型规则决定。

### 5.4 文件状态机

```text
DRAFT → IN_REVIEW → READY → SUBMITTED → RECEIVED
  ↑          ↓                     ↓
  └──── RETURNED              APPROVED / ISSUED / ARCHIVED
```

每次修改生成新的 `DocumentVersion`。`SUBMITTED` 之后的原版本不可修改；退回后基于原版本建立修订版。

### 5.5 Agent 任务状态机

```text
QUEUED → RUNNING → COMPLETED
             ├── FAILED
             ├── CANCELED
             └── DISCARDED
```

`CANCELED` 表示运行时已请求停止；`DISCARDED` 表示供应商仍返回结果，但生成租约已失效，输出被拒绝进入任何正式记录。

## 6. Agent Harness

### 6.1 角色运行配置

每个重要角色包含四层信息：

1. **稳定身份**：履历、职务、权限、能力、沟通风格、风险偏好、价值排序和底线；
2. **动态工作状态**：任务、工作量、压力、当前立场、日程和行动计划；
3. **局部世界视图**：`Belief`、可见决定、亲历事件和有权读取的文件；
4. **私人记忆**：对人物、谈话、承诺和失败的角色化理解。

稳定身份之外，每个角色还拥有公开工作关系圈。市内干部可以识别完整市级组织名册中的基本资料，外部和上级角色按职责获得相关联系人；关系圈只含公开身份、工作风格和组织关系，不包含目标、认知或私人记忆。

稳定配置不能由 Agent 自己重写。动态状态只能通过领域事件改变。

### 6.2 上下文构建

`ActorContextBuilder` 每次调用按以下顺序构建最小上下文：

1. 不可覆盖的角色与安全规则；
2. 当前职务、权限和工具能力；
3. 当前内容包的公共背景资料；
4. 当前场景、参与者、时间与任务；
5. 与当前议题相关的 `Belief` 及来源；
6. 检索到的情节记忆；
7. 可访问文件的元数据和必要摘录；
8. 当前对话或会议记录；
9. 输出模式和工具模式。

当前上下文投影检索最多 14 条动态认知、10 条高相关/高重要性记忆、10 条未完成待办、8 条相关承诺和最近 24 个当前场景发言。完整旧场景和完整文件正文不直接塞入 Prompt，由 Agent 工具按权限读取。

禁止注入：

- 完整世界状态；
- 其他人物的私聊和私人记忆；
- 角色没有读过的文件；
- 尚未通过渠道传播的隐藏事实；
- 能让角色绕过权限的内部实现说明。

Agent 声称事实时必须返回 `belief_id`、`document_version_id` 或标记为推断/传闻。无法映射的确定性事实陈述被拒绝或改写为不确定表达。

公共背景资料有稳定的 `reference_material_id`，每名角色都可引用；它不进入角色私人 `Belief`，也不会因为某个角色引用而被当作玩家新发现的隐藏事实。当前 MVP 将十份压缩后的公共资料随角色上下文注入；资料继续增长后改为按地点和议题检索，但必须保持全员可访问。

### 6.3 记忆分层

| 层 | 内容 | 是否可压缩 |
|---|---|---|
| 结构化事实 | 任务、承诺、决定、文件、证据、责任 | 不可只靠摘要保存 |
| 语义记忆 | 对人物的稳定看法、长期目标和反复模式 | 可合并，但保留来源 |
| 情节记忆 | 某次会谈、会议、冲突或受辱的角色化回忆 | 可压缩，保留重要节点 |
| 工作记忆 | 当前场景所需材料与最近对话 | 场景结束后清除或归档 |

每次场景结束会冻结完整参与者、逐字记录、结论与日期。情节记忆可以压缩，但参与者仍能通过 `list_scene_records` 与 `read_scene_record` 回读自己的完整亲历记录。

记忆检索按议题、人物、地点、时间、情绪强度和未完成义务排序。正式记录即使不在 Prompt 中，也不会从世界中消失；“遗忘”只影响人物在当前语言推理中是否想起。

矛盾记忆不能被总结成虚假的统一结论。系统保留人物在不同时间的说法和其当时可见来源。

### 6.4 Agent 调用类型

- `speech_intent`：判断当前轮是否希望发言，只输出布尔值和意图；
- `utterance`：在获得发言权后生成完整发言；
- `conversation_reply`：生成个别面谈回复；
- `post_scene_reflection`：提取该角色听到的内容并提出后续意图；
- `daily_intention`：日终为被激活角色提出有限行动；
- `document_draft`：基于授权材料起草或修订文件；
- `superior_reaction`：上级对报告或面谈提出即时或延迟反应意图；
- `narration`：把已经结算的现场和后果转写成玩家文本；
- `memory_compaction`：压缩角色情节记忆。

不同调用使用不同 Prompt 和 Pydantic 模式，不能用一个“万能 Agent”响应所有任务。

### 6.5 工具能力

Agent 可获得的游戏内工具按角色、场景和任务动态授权：

| 工具 | 作用 | 是否直接改变世界 |
|---|---|---|
| `file_search` | 搜索有权限的文件元数据 | 否 |
| `file_read` | 读取指定可见版本 | 否 |
| `file_create_draft` | 创建个人或机构草稿 | 只创建草稿 |
| `file_revise_draft` | 基于现有草稿产生新版本 | 只创建版本 |
| `file_submit` | 报送一个就绪版本 | 产生报送记录，不自动产生政策效力 |
| `request_information` | 向有渠道的人或机构提出材料请求 | 生成任务 |
| `contact_actor` | 向另一角色发起通气、询问或转告 | 生成有界沟通任务 |
| `schedule_request` | 请求会议、面谈或日程 | 生成待协调日程 |
| `propose_action` | 提议准备或实施某项行动 | 生成 `ActionIntent` |
| `list_contacts` | 查询本人物认识的上下级、同级和利益相关方公开资料 | 否 |
| `list_scene_records` / `read_scene_record` | 查询本人物亲历的冻结场景 | 否 |
| `record_knowledge` | 保存带来源与置信度的动态认知 | 只更新本人物认知 |
| `record_memory` | 保存带重要性与原始记录引用的私人记忆 | 只更新本人物记忆 |
| `record_todo` | 保存待办、期限与正式程序要求 | 只创建待办 |
| `record_relationship_impression` | 保存本人物对特定对象的工作关系判断 | 只更新主观关系 |
| `record_commitment` | 保存交办、承诺或条件交换 | 创建结构化义务记录 |

对话回复和获得发言权后的会议发言使用相同的原生 Tool Calls 协议。工具通过 Chat Completions 请求顶层的 `tools` 注册，调用从 `message.tool_calls` 读取，执行结果以带 `tool_call_id` 的 `role: tool` 消息回传；模型完成工作时单独调用终止工具 `submit_final_result`。一次人物 Agent Loop 最多运行 128 轮，这是运行时硬上限；Prompt 同时把 32 轮内完成设为强目标，要求人物避免重复调用同一工具、反复读取同一材料或检索无关内容，并在信息足够时立即提交最终结果。每轮可由供应商返回一个或多个工具调用。工具写操作先生成 `AgentToolEffect`，待最终文本、认知引用和场景记录版本全部校验成功后统一提交。

Harness 对完全相同的工具名和参数建立调用签名。重复调用不会再次执行，下一轮强制指定 `submit_final_result`；第 32 轮起所有请求均指定终止工具。普通正文冒充结果、工具参数解析失败、终止工具与其他工具混用或终止参数不符合模式时只允许有限修复；连续三次仍失败则丢弃全部暂存副作用。人物发言任务返回一句可见但不创造事实的安全答复，场景结算任务返回无新增判断的安全结果。供应商不可用、超时、输出截断和内容过滤仍明确报错，不伪装成成功。

不得在普通消息正文中要求模型手写 `{tool_calls, final}` 信封。原生工具参数仍需经过 Pydantic 校验；参数 JSON 不完整时把错误作为工具结果返回，允许人物在后续轮次修复。若供应商返回 `finish_reason=length`、内容过滤或资源不足，Harness 必须给出对应的可诊断错误并丢弃本轮全部暂存副作用。

`propose_action` 的参数至少包括：

```json
{
  "action_type": "verify_employment_list",
  "objective": "核实受影响职工名单",
  "target_ids": ["beishan_county"],
  "earliest_date": "2026-09-02",
  "due_date": "2026-09-05",
  "visibility": "internal",
  "resource_request": [],
  "authority_claim": "industry_coordination_duty",
  "supporting_document_ids": [],
  "expected_output": "verification_report"
}
```

工具调用只表达“角色准备做什么”。`ActionGate` 将结果分类为：

- 可在现有权限内直接执行；
- 只能进行准备或调查；
- 需要玩家授权；
- 需要特定会议、签发或行政程序；
- 因资源不足暂不可行；
- 越权、违法或与已知事实冲突。

### 6.6 安全边界

Agent 永远没有：

- 主机文件系统读写；
- Shell 或任意代码执行；
- 任意互联网访问；
- 数据库直接写入；
- 伪造签名、表决、批准或系统事件的能力；
- 读取其他角色完整 Prompt、私人记忆或隐藏事实的能力。

## 7. 会议编排

### 7.1 发言意愿并行阶段

在自由磋商每一轮，`MeetingOrchestrator` 为每名在场 Agent 构建基于同一记录版本的上下文，并并行调用 `speech_intent`。

输出示例：

```json
{
  "wants_to_speak": true,
  "responds_to_turn_id": "turn_18",
  "intent": "challenge_funding_assumption",
  "urgency": "normal"
}
```

如果多个结果为真，领域随机源从候选集合中选择一人。随机抽样输入、标签与结果写入事件日志。`urgency` 只供 UI 和未来平衡使用，首版不改变均匀抽样规则。

### 7.2 发言生成与提交

只有获选角色调用 `utterance`。生成过程拥有：

- `generation_id`；
- 场景记录版本；
- 取消令牌；
- 最晚完成时间；
- Prompt 版本；
- 流式临时缓冲区。

完整输出校验通过且记录版本未变化时，才追加正式 `SpeechCommitted`。流式文本只是临时展示。

会议启动时，应用服务把玩家选定且有权访问的文件复制为 `MeetingMaterial` 快照，记录 `document_id`、版本、正文、发送阶段和全体与会者 ID。参会 Agent 的可见文件投影和文件工具优先读取该快照；未参会人物不获得权限。会中追加材料是一条携带会话版本、幂等键和会议记录版本的命令，会追加系统记录并递增记录版本；人物发言正在生成时须先等待或打断，防止旧上下文发言覆盖新材料。

当前实现对人物发言请求启用 DeepSeek Chat Completions 流式响应。Harness 累积原生 `tool_calls[].function.arguments`，只从终止工具 `submit_final_result` 的 `text` 字段提取已经完整到达的字符串字符，不向网页暴露其他工具参数。进程内临时缓冲以 `generation_id` 和递增修订号保存当前全文、人物、阶段和状态，`GET /api/games/{id}/stream` 通过 SSE 推送快照；前端收到新快照后直接渲染其中的当前全文，不使用定时器拆字或人为控制显示速度，页面节奏完全由模型分块和 SSE 到达节奏决定。工具副作用、文本和认知引用仍在最终校验后一次性写入存档，临时缓冲不占用存档版本。

同一 SSE 连接在 `debug=1` 时额外推送 Agent 调试事件。首次连接发送当前轨迹快照，之后只发送新增事件，避免长轨迹反复全量传输。事件包括任务、轮次、工具名称、参数字段、结果类型、成功或错误、收敛保护和终止状态；服务端在入缓冲前过滤 Key，并把工具参数值、私有记忆、内部行动、不可见文件正文和隐藏推理压缩成计数或类型摘要。并行场景结算只有在整个批次完成后才标记完成，单个人物先结束不会提前关闭批次状态。

### 7.3 玩家中断

玩家提交发言时，应用服务：

1. 原子递增场景记录版本；
2. 使当前 `generation_id` 的租约失效；
3. 请求取消模型任务；
4. 向 SSE 推送临时输出撤回事件；
5. 校验并提交玩家发言；
6. 从新记录版本开始下一轮。

迟到的模型返回因版本不匹配进入 `DISCARDED`，不得写入转录、记忆、Token 化文件或领域事件。

### 7.4 正式会议

正式会议在语言互动之外还要经过：

- 会议权限检查；
- 成员与列席身份；
- 法定人数与回避；
- 议题准备程度；
- 主持、讨论、归纳；
- 逐项表决或退回；
- 纪要、签发与后续程序。

表决意图可以由角色 Agent 提出，最终票值、门槛和结果由规则内核计算。玩家不能用自由文本把列席人员变成有表决权的成员。

### 7.5 会后结算的并发与上限

所有参会者可以并行生成 `post_scene_reflection`，但结果按稳定顺序提交：

1. 先提交各自认知和记忆提议；
2. 再提交沟通、文件和行动意图；
3. `ActionGate` 统一处理权限与冲突；
4. 每人首版最多保留 2 个后续意图；
5. `contact_actor` 只展开一跳，回复进入日终或下一日。

这样既允许会后通气，又防止模型形成无限自主对话链。

## 8. 个别面谈、调研和向上汇报

### 8.1 个别面谈

使用与会议相同的 `SceneOrchestrator`，但参与者通常只有玩家与一名 NPC。渠道、在场秘书、是否有记录和保密预期决定谁能在事后获得内容。

场景提交前只记录语言；承诺、交办、关系和后续行为在场景结算中结构化生成并由规则校验。

### 8.2 现场调研

`FieldVisitResolver` 在叙事前确定：

- 是否通知、何时通知、谁知道；
- 地点与访问范围；
- 当时在场人物和可观察对象；
- 布置、隐瞒、样本偏差与偶然因素；
- 玩家能直接观察、只能听说和仍不可见的内容。

现场 Agent 只能基于其角色和当场可见内容回答。叙事 Agent 不得添加未结算事实。

### 8.3 上级报告

书面报告本质是 `DocumentVersion + Submission`。上级收到的上下文包含文件来源、签发、附件、报送时间、已知矛盾和该上级自己的优先事项。

`superior_reaction` 输出可包括：

```json
{
  "immediate_reply": "要求补充就业影响测算",
  "reaction_kind": "conditional_follow_up",
  "condition": "report_revision_received",
  "time_window_days": [2, 7],
  "expires_after_days": 14,
  "proposed_action": "schedule_review_meeting"
}
```

规则内核可以接受、调整为合法范围、要求补充条件或拒绝该意图。没有安排后续不代表系统忘记文件；上级的认知与评价仍可被以后检索。

## 9. 虚拟文件系统

### 9.1 文档库而非真实目录

前端可以把文档展示为“收件箱、草稿、共享文件、已提交和归档”等文件夹，但后端使用带访问控制的文档实体，不把自由路径直接映射到磁盘。

玩家完成批注、退回、转办或报送后，文件记录 `handled_date`；当日结束并进入下一日期时自动转为 `ARCHIVED`。归档不删除正文、来源、版本、收件人或工作记录，也不阻止已经建立的延迟反馈读取原文件。

建议的逻辑视图：

```text
/actors/{actor_id}/inbox
/actors/{actor_id}/drafts
/offices/{office_id}/shared
/meetings/{meeting_id}/materials
/issues/{issue_id}/dossier
/submissions/sent
/archive
```

路径只是查询视图；权限依据角色、机构、收件人、密级和领域事件计算。

### 9.2 文件内容与事实引用

文档正文可由 Markdown 片段和结构化附件组成。重要主张保存可选的来源引用：

- `belief_id`；
- 其他 `document_version_id`；
- `observation_id`；
- 明确标记的估算、传闻或作者判断。

Agent 可以有偏见、遗漏或选择性表述，但不能把角色完全不知道的隐藏事实写成确定结论。

### 9.3 正式效力

文件的“写完”“提交”“批准”“签发”“公开”和“已经执行”是不同状态：

```text
写出草稿 ≠ 已提交
已提交 ≠ 已批准
已批准 ≠ 已签发
已签发 ≠ 已完成后续法定程序
正式文件存在 ≠ 执行已经发生
```

文件工作流服务负责版本与流转，模拟内核负责判断它在当前权限和程序下产生何种效力。

### 9.4 会议级文件共享

- 会前选择与会中临时追加都只能使用玩家可读文件；
- 共享保存发送时版本快照，不直接扩张原文件的收件人或永久访问控制；
- 同一文件的不同版本可以分别进入会议，相同版本不得重复发送；
- 会议记录冻结后，材料快照随场景档案保存，亲历者可通过受限场景记录回读；
- 将文件发给会议只改变知情范围，不改变文件的批准、签发或正式效力。

## 10. 日程与后台任务

### 10.1 行动点预留

预约未来行动时：

- 确定日期会预留对应行动点；
- 暂定日期只显示潜在冲突，不锁定预算；
- 实际开始时扣点；
- 提前合规取消释放预留；
- 同日取消、缺席或被强制打断的成本由行动规则决定。

### 10.2 NPC 日程

NPC 也拥有简化日程和工作量。是否参加会议由职务义务、已有日程、地点、关系和紧急性决定。Agent 表达接受或拒绝理由，规则服务验证不能违反的职务约束。

### 10.3 后台任务

起草文件、核查数据、联系单位和准备会议不占玩家行动点，但占执行者的工作量和游戏时间。`Task` 保存负责人、依赖、预计完成日、质量基线、优先级和失败原因。

同一人物任务过载会降低速度和质量，或促使其转交、拖延、选择性完成和请求资源。

## 11. 日终结算流水线

日终结算必须是可重试但只提交一次的事务流程：

1. `CloseDayCommand` 校验日状态和会话版本；
2. 冻结玩家本日输入；
3. 完成到期任务和已排队文件生成；
4. 根据任务、责任、临近期限、近期场景和事件条件选择活跃角色；
5. 并行获取活跃角色的有限 `daily_intention`；
6. 规范化并去重沟通、文件和行动意图；
7. `ActionGate` 做权限、程序、资源、依赖和冲突检查；
8. 模拟内核按确定顺序执行获准命令；
9. 使用派生随机流结算执行偏差和外部事件；
10. 传播可被各渠道感知的事实，更新 `Belief`；
11. 更新任务、承诺、关系、证据、指标和延迟触发器；
12. 生成新闻、来文和报告任务；
13. 压缩记忆；
14. 产生新快照与下一日晨报；
15. 在一个事务中提交事件日志、快照和玩家消息。

任一必需步骤失败则本日仍处于 `END_DAY_REQUESTED` 或可恢复错误状态，不产生半个明天。

## 12. 动态事件系统

### 12.1 事件来源

- 固定在日历上的制度义务和期限；
- 状态阈值与组合条件；
- NPC 已获准行动的后果；
- 任务逾期、承诺违约和文件矛盾；
- 带前置条件的外部事件候选池。

### 12.2 事件候选而非时间脚本

内容包定义候选事件的：

- 前置条件；
- 不兼容条件；
- 最早/最晚窗口；
- 基础权重和冷却；
- 允许影响的指标范围；
- 可涉及的角色和地点类型；
- 产生的结构化事实与后续触发器。

模拟内核筛选并抽样；LLM 只生成表达、标题和不影响规则的细节。内容包不得写成“第 7 天必然发生银行停贷、第 12 天必然省级复核”的固定轨道。

### 12.3 延迟触发器

`DelayedTrigger` 必须有：

- 来源事件或人物；
- 触发条件；
- 最早时间、最晚时间或过期条件；
- 触发概率所使用的随机流标签；
- 触发、取消、休眠和关闭状态；
- 触发后允许创建的领域命令。

如果上级 Agent 选择“暂不处理”，可以只更新记忆和评价，不一定创建触发器。永久不触发的事项应明确关闭，而不是永远参与每日扫描。

## 13. API 草案

### 13.1 会话、日期和晨报

- `POST /api/games`：创建游戏；
- `GET /api/games/{id}`：获取玩家可见快照；
- `GET /api/games/{id}/days/current`：获取当日状态；
- `GET /api/games/{id}/briefings/current`：获取晨报；
- 玩家快照中的 `reference_materials`：获取当前内容包的公共市情资料；
- `POST /api/games/{id}/days/current/close`：结束一天；
- `GET /api/games/{id}/stream`：SSE 进度、流式文本和撤回事件；查询参数 `debug=1` 时附加经过玩家可见性过滤的 Agent 行为轨迹。

### 13.2 日程与行动

- `GET /api/games/{id}/calendar`；
- `POST /api/games/{id}/calendar-entries`；
- `PATCH /api/games/{id}/calendar-entries/{entry_id}`；
- `POST /api/games/{id}/field-visits`；
- `POST /api/games/{id}/superior-reportings`。

### 13.3 场景

- `POST /api/games/{id}/meetings`；
- `POST /api/games/{id}/conversations`；
- `POST /api/games/{id}/scenes/{scene_id}/start`；
- `POST /api/games/{id}/scenes/{scene_id}/player-speeches`；
- `POST /api/games/{id}/scenes/{scene_id}/nominate-speaker`；
- `POST /api/games/{id}/scenes/{scene_id}/close`；
- `POST /api/games/{id}/scenes/{scene_id}/cancel-generation`。
- `POST /api/games/{id}/scenes/{scene_id}/materials`：向进行中的会议追加一个或多个玩家可读文件版本。

创建会议与会议日程的请求可携带 `meeting_document_ids`，服务端在会议建立或日程预约时冻结对应版本。

### 13.4 文件

- `GET /api/games/{id}/documents`；
- `GET /api/games/{id}/documents/{document_id}/versions/{version_id}`；
- `POST /api/games/{id}/documents/{document_id}/annotations`；
- `POST /api/games/{id}/documents/{document_id}/return`；
- `POST /api/games/{id}/documents/{document_id}/forward`；
- `POST /api/games/{id}/documents/{document_id}/submit`；
- `POST /api/games/{id}/document-tasks`。

### 13.5 玩家笔记

- `POST /api/games/{id}/notebook-notes`；
- `PATCH /api/games/{id}/notebook-notes/{note_id}`。

笔记写接口同样携带会话版本和幂等键，但不需要模型调用，也不消耗行动点。`notebook_notes` 只出现在玩家 DTO 中；`AgentContextBuilder`、可见文件列表、人物记忆和工作记录组装器均不得读取该容器。

所有写接口携带会话版本和幂等键。场景发言还携带当前记录版本；过期版本返回冲突而不是静默覆盖。

## 14. 网页端信息架构

主界面采用“领导工作台”：

- 顶部：日期、职位、剩余行动点、当前时段和日终按钮；
- 左栏：晨报、议题、待办与收件箱；
- 市情资料：城市总览和县区概况，只读且不参与文件审批流；
- 中栏：当前文件、会议、面谈、调研或报告场景；
- 右栏：今日日程、相关人物、期限和承诺提醒；
- 日历：未来日程、行动点预留、准备依赖和冲突；
- 文件中心：收件、草稿、送审、已发、归档和版本沿革。
- 私人笔记本：玩家可在日常工作或收起面谈后记录要点；笔记与正式文件、Agent 记忆和工作记录分离。

个别面谈场景允许前端保持 `active_scene` 不变并切换到案头标签。场景组件保留挂载，避免丢失流式显示进度；页面显示持续的“返回面谈”入口。该切换是纯 UI 状态，不提交领域命令，也不改变记录版本。

会议界面必须显示：

- 会议制度类型与讨论方式；
- 出席、列席、缺席和表决资格；
- 当前议题、材料和发言记录；
- 会前材料的标题、版本与正文，以及从玩家文件列表临时追加材料的入口；
- “NPC 正在形成发言”的可中断状态；
- 玩家发言、点名、转议题、表决、退回和结束会议操作；
- 哪些结论只是意见，哪些已经取得正式效力。

顶栏提供默认关闭的 Agent 调试开关。没有运行任务时面板折叠为状态条；任务开始后自动展开，并停靠在不遮挡发言/打断按钮的一侧。面板展示当前或最近一次任务的增量行为事件，不得成为读取 NPC 私有状态的旁路。

## 15. 确定性、并发与成本

### 15.1 随机流

每局使用主种子派生独立随机流：

- `meeting_speaker`；
- `execution`；
- `information_spread`；
- `external_event`；
- `field_observation`；
- `delayed_trigger`。

事件日志保存抽样标签、候选集合、流位置与结果。

### 15.2 并发原则

可以并行：

- 同一会议轮所有角色的发言意愿；
- 场景结束后各角色的独立反思；
- 日终不同角色的行动意图；
- 相互无依赖的文档起草。

必须串行或稳定排序：

- 正式发言提交；
- 同一文件版本变更；
- 相互冲突的行动验证与执行；
- 领域事件落库；
- 日期推进。

### 15.3 成本控制

- 普通读文件、查看日程和结构化批示不调用 LLM；
- 发言意愿使用短输出；
- 只有获选发言者生成完整文本；
- 日终只激活相关角色；
- 文件先检索元数据，再按需注入摘录；
- 记忆使用检索而非每次塞入全历史；
- 会后和日终行动数量有硬上限；
- 模板模式覆盖完整日循环。

## 16. 持久化与迁移

采用事件日志加周期快照：

- `DomainEvent` 只追加；
- 每日结算完成后保存世界快照；
- 场景记录、文档版本和提交记录独立持久化；
- 随机流位置、Prompt 版本和内容包版本进入存档；
- 存档导出可以重建同一状态。

首个逐日 MVP 复用了 SQLite 中已有的存档 JSON 列，没有修改已经发布的表结构。当前快照模式版本为 5；版本 2、3、4 的逐日存档可在读取时补齐动态认知、关系圈、承诺、场景档案、玩家笔记和会议材料容器，旧六回合原型仍会被识别并提示新建。首次需要增加或修改独立数据库列之前必须引入 Alembic，不能在应用启动时偷偷改表。

同一逐日内容包新增人物时，读取层会为旧快照补齐该人物的关系基线、运行时容器和初始认知索引，但不改变存档版本，也不覆盖已有角色状态；玩家下一次提交领域命令时才把补齐后的快照正常保存。联系人目录由玩家视图中的分组字段完整渲染，不能用前端切片截断角色集合。

## 17. 测试策略

### 17.1 领域测试

- 每日行动点扣除、预留、取消和冲突；
- 日程到日自动触发与上级强制插入；
- 文件版本不可变、权限和正式效力；
- 会议类型、法定人数、列席和表决；
- 场景结束后行动意图的权限分类；
- 承诺、任务、延迟触发器和过期；
- 同种子的发言人抽样、调研观察和日终事件；
- 玩家 DTO 与 Agent Context 不泄漏隐藏事实。

### 17.2 Agent 契约测试

- 每个调用类型均符合独立模式；
- 角色只引用可用认知和文件；
- 被取消发言永远不进入记录与记忆；
- 会前与会中材料按版本冻结，只对全体与会者可见，未参会者和玩家无权文件均被拒绝；
- 文书起草保留来源、版本和不确定性；
- `propose_action` 不直接改变状态；
- 上级反应不会越过权限或创建无限触发器；
- Prompt 失败只有限重试，之后安全降级。
- 重复工具调用在下一轮强制终止，第 32 轮后不再执行非终止工具，连续终止协议失败会形成可见安全答复；
- 调试轨迹顺序稳定、批次状态不会提前完成，并过滤 Key、私有记忆、内部行动和不可见文件正文。

### 17.3 集成与回放

- 无 LLM 连续运行至少 7 个游戏日；
- 一天内完成文件批阅、面谈、会议、日终和次日晨报；
- 多人自由磋商出现无人、一人和多人希望发言三种情况；
- 玩家中断正在生成的发言；
- 预约未来调研并在执行日扣点；
- 让秘书起草报告，玩家签发后提交上级并得到延迟反馈；
- 保存、重载和继续运行结果一致；
- 重复幂等请求不重复扣点、推进或报送文件。
